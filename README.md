# Workbuddy搭建博客的全过程记录（真实建站实录-踩坑记录）

---
title: 一次真实建站实录-踩坑记录
---

> 这篇文章是我自己搭这个博客的全过程记录。不是教程式的「第一步第二步」，而是把当时真实的决策、真实的报错、以及排查了半天才找到的几个坑，按顺序写下来。如果你也打算用「静态页面 + 云数据库」的方式建站，这里的每一条大概都能帮你省几个小时。

## 一、先把「不做什么」说清楚

需求很朴素：文章列表、文章详情、相关阅读、标签分类、关于页，支持 Markdown 渲染，文章存云端数据库、图片与附件走云端存储、带登录认证，最后能发布上线。

真正决定后面所有事情的，其实是选型阶段**砍掉**的东西：

- **不做前后端分离。** 没有 Node 服务、没有 API 层、没有接口文档。
- **不引入构建工具。** 不装打包器，没有 `package.json`，没有 `dist/`。
- **前后端边界直接由数据库权限来描述。** 谁能读、谁能写，全部写成数据库的行级安全（Row Level Security，RLS）策略，而不是写成服务端代码里的 `if`。

于是最终形态是：**几个静态 HTML 页面，直连一套云数据库 / 云存储 / 邮箱登录服务**。浏览器通过 CDN 引入的 SDK 直接访问数据库，权限判定发生在数据库侧。

好处很实在：改一行文案不用重新构建，部署就是传文件；坏处也很实在——**所有权限逻辑都挤在数据库里，一旦策略写漏，页面看起来完全正常，但数据其实已经裸奔了。**

这句话在后面会变成一个真实的坑。

## 二、目录结构：六个页面 + 一个公共模块

```
tech-blog/
├── [index.html](https://tech-blog-81910.app.workbuddy.host/index.html)      # 列表：精选 + 卡片流 + 搜索 + 标签筛选 + 分页 + 侧栏
├── post.html       # 详情：Markdown 正文 + 目录 + 代码高亮 + 附件 + 相关阅读
├── tags.html       # 标签：按标签分组聚合
├── about.html      # 关于：[站长资料](https://tech-blog-81910.app.workbuddy.host/about.html)
├── login.html      # 登录：密码 / 验证码 / 注册 / 找回
├── admin.html      # 写作后台：新建、编辑、发布、删除、上传
└── assets/
    ├── cloud.js    # 云客户端封装 + Markdown 管线 + 导航页脚 + 工具函数
    └── style.css   # 设计系统
```

`cloud.js` 是一个大 IIFE（立即执行函数），作用域内的能力统一挂到全局的 `window.Blog` 上，其余页面 `<script>` 直接调 `Blog.xxx()`。

——「IIFE」和「统一挂到全局」，后面各会变成一个坑。

## 三、数据库：三张表，一道权限模型

### 3.1 表结构

| 表              | 用途        | 关键设计                                   |
| -------------- | --------- | -------------------------------------- |
| `posts`        | 文章        | `owner_id` 默认值就是 `auth.uid()`，归属由数据库决定 |
| `attachments`  | 附件元数据     | 可见性跟随所属文章，策略里用 `EXISTS` 子查询关联          |
| `site_profile` | 站点 / 博主资料 | 供首页侧栏与关于页读取                            |
| `site_admins`  | 发文白名单     | 客户端完全不可读，只能通过函数拿布尔值                    |

### 3.2 归属：客户端永远不发送 `owner_id`

`owner_id` 的默认值写成 `auth.uid()`，插入时**由数据库自动填当前登录用户**，前端一个字都不发。

这一点看着不起眼，但它决定了越权的上限：**只要客户端无法自己声明归属，就没有「伪造他人身份发文」这条路径。**

### 3.3 建表和 RLS 是两道门

这里有个容易踩的地方：**建表和 RLS 是两件事**。要先把表 `GRANT` 给 `authenticated` / `anon` 角色，再 `CREATE POLICY` 建策略。

如果只建了策略、忘了 `GRANT`，你会收到一个 `42501 permission denied`——这个报错**看起来像策略没生效，实际上是请求压根没走到策略那一层**。查这类问题时，先确认 GRANT，再看策略。

## 四、Markdown 渲染管线

正文以 Markdown 存在 `content_md` 字段里，渲染时走一条固定的管线：

```js
function markdownToHtml(md) {
  var html;
  if (window.marked) {
    html = window.marked.parse(md, { gfm: true, breaks: false, headerIds: false });
  } else {
    html = '<p>' + escapeHtml(md).replace(/\n/g, '<br>') + '</p>';
  }
  // 一定要过一遍白名单过滤：Markdown 里是可以塞原始 HTML 的
  if (window.DOMPurify) {
    html = window.DOMPurify.sanitize(html, { ADD_ATTR: ['target', 'rel', 'id'], ADD_TAGS: ['iframe'] });
  }
  return html;
}
```

三点说明：

1. **`marked` 负责解析，`DOMPurify` 负责消毒。** 少了后一步，文章正文就是一个 XSS 入口——Markdown 语法里允许直接写 HTML。
2. **渲染完再做增强。** 给 `H2/H3` 注入锚点 id 并收集目录数据；给每个 `<pre>` 包一层带「复制」按钮的工具条；用 `highlight.js` 对代码块按语言高亮。
3. **降级要优雅。** `marked` 没加载成功时退回转义后的纯文本段落，而不是白屏。

封面也做了两级降级：文章存外链地址就直接用；存的是云端存储路径，就换取一次性的签名地址；连签名都拿不到（比如未登录访客），回退到「渐变背景 + 标题」的占位封面。**宁可显示一个设计过的占位图，也不要一个破图的图标。**

## 五、八个坑

下面这八条就是当时真实花掉时间的地方。我把现象、定位思路和修法都写全，因为\*\*「怎么找到它的」往往比「怎么修的」更值得记。\**

### 坑 1：详情页正文一片空白——查询字段漏了正文

**现象**：列表页一切正常，点进详情页，标题、摘要、标签、目录框都在，**唯独正文区域是空的**。

**定位**：先在控制台看一眼拿到的数据，发现对象里根本没有 `content_md` 这个字段——不是渲染失败，是**压根没查出来**。

**原因**：列表和详情共用了同一个查询字段常量。列表不需要正文（省流量），于是那个常量里不含 `content_md`；详情页直接复用了它。

```js
// 列表用：不含正文
var POST_FIELDS = 'id,owner_id,title,slug,summary,tags,status,...';

// 详情 / 编辑器用：必须带上正文
var POST_DETAIL_FIELDS = POST_FIELDS + ',content_md';
```

**修法**：拆成两个常量，各取所需。

**启示**：字段常量「复用」是个陷阱。列表和详情的字段需求**天然不同**，硬要共用，一旦需求分叉，就会以「页面看起来正常但内容为空」这种静默方式炸掉。

### 坑 2：`[hidden]` 失效，元素藏不住

**现象**：给提示框、按钮加了 HTML 的 `hidden` 属性，页面刷新后它**照样显示**。

**原因**：`hidden` 不是魔法，它只是浏览器默认样式表里的一条 `display: none`。而自定义样式 `.notice { display: flex }` 这类**类选择器的优先级高于 UA 样式表**，于是把 `hidden` 覆盖掉了。

**修法**：在样式表里显式补一条兜底规则。

```css
[hidden] { display: none !important; }
```

**启示**：凡是依赖「浏览器默认行为」的写法，都要确认它没有被自己的样式表盖掉。

### 坑 3：媒体查询被写在后面的基础规则覆盖

**现象**：移动端导航该显示的时候死活不显示。

**原因**：`.mobile-nav { display: none; }` 这条基础规则，被放在了媒体查询**之后**。两条规则优先级相同，**后面的赢**，于是移动端的 `display: flex` 永远被压住。

**修法**：基础规则必须写在媒体查询**之前**。

```css
/* 先写基础规则 */
.mobile-nav { display: none; }

/* 再写断点覆盖 */
@media (max-width: 720px) {
  .mobile-nav { display: flex; }
}
```

**启示**：CSS 是「层叠」的，书写顺序本身就是逻辑。

### 坑 4：IIFE 里新加了函数，忘了导出

**现象**：页面控制台报 `Blog.isSiteAdmin is not a function`。

**原因**：`cloud.js` 末尾的导出对象是一份**手写清单**：

```js
window.Blog = {
  // ...
  listTags: listTags,
  countPublished: countPublished,
  // 新加的 isSiteAdmin 忘了写在这里
};
```

函数在作用域内定义好了，页面里也调用了，就是没被挂出去。**这就是「统一挂到全局」这个约定的代价：它靠人记性维持。**

**修法**：补一行。并且养成一个自检习惯——**新增函数后立刻搜一次函数名，它应该在文件里出现两次：定义一次，导出一次。**

### 坑 5：登录明明成功了，却进不去后台（无限往返登录页）

这是八个坑里最隐蔽的一个，也是唯一一个\*\*「已经通过了测试」\*\*的坑。

**现象**：用邮箱密码登录成功，首页导航也正确显示已登录状态。但一访问写作后台，立刻被弹回登录页；在登录页再登录一次，又被弹回去。**死循环。**

**定位过程**（三步排除法）：

1. 查数据库：账号注册成功、密码哈希正常、`last_login` 有值 → **登录本身没问题**。
2. 用真实账号跑一遍：登录成功，且权限函数返回 `true`，说明该账号**有发文权** → **不是权限问题**。
3. 既然既不是登录问题也不是权限问题，那只剩一种可能：**页面把「已登录」判断成了「未登录」。**

**根因**：登录守卫的写法是这样的——

```js
// 页面里（admin / post / about / login 四个页面都这么写）
Blog.mountChrome('admin').then(function (session) {
  if (!session) { location.href = 'login.html'; return; }
  // ... 渲染后台
});
```

而 `mountChrome` 的实现里：

```js
return getSession().then(function (session) {
  renderAuthSlot(session);
  // ... 渲染导航、页脚，绑定事件
  // ← 问题就在这：没有把 session 返回出去
});
```

回调函数里**没有 `return session`**，所以整个 Promise 的决议值恒为 `undefined`。守卫拿到 `undefined`，判定「未登录」，跳转登录页；登录完成后回来，还是 `undefined`——循环。

**修法**：一行。

```js
return session || null;
```

一处修复，四个页面同时恢复正常。

**为什么一直没被发现**：因为之前的验证里只断言了「**未登录**访问后台 → 会被跳转到登录页」这一条。而这条断言**恰好是通过的**——守卫确实把所有人都拦下来了，包括本该放行的人。**一条通过的测试，掩盖了半边功能完全不工作。**

**这是本文最值钱的一条经验：受保护的页面，正反两条路径都要断言。**「进不去」要测，「进得去」同样要测；「陌生人被拒绝」要测，「本人被放行」更要测。

### 坑 6：通过邮箱加进白名单的人，文章对访客不可见

**背景**：站点改成了「白名单多作者」——注册入口公开，任何人都能注册登录并进入后台，但**不在名单里就发不了文**。名单表 `site_admins` 有 `email` 和 `owner_id` 两列。

**现象**：通过邮箱加进白名单的账号，发布文章后自己后台能看到，**但访客在首页、标签页都看不到**。也就是「发了，但等于没发」。

**原因**：文章可见性判断函数 `is_site_author(owner_id)` 原先只比对 `site_admins.owner_id`。而通过邮箱加入名单时，用户**还没注册、没有 uid**，那一行的 `owner_id` 是 `NULL`——于是白名单行匹配不上文章真正的 `owner_id`，文章被判定为「非白名单作者的作品」，不对访客公开。

**修法**：让函数能在拿到 `owner_id` 之后**反查该用户的邮箱**，再和邮箱白名单比对。

```sql
-- 由 uid 反查邮箱（sub 就是 auth.uid()）
select lower(btrim(u.email)) from auth.users u where u.sub = target_owner
```

这个函数建为 `SECURITY DEFINER`，实测在匿名访客的上下文里也能读 `auth.users`。

**启示**：白名单有「按 uid」和「按邮箱」两种录入方式，而**校验逻辑必须同时覆盖两者**，否则就会出现「一行数据看着加进去了，实际不生效」的静默失效。

### 坑 7：关于页被协作者顶掉了

**现象**：关于页（https://tech-blog-81910.app.workbuddy.host/about.html）显示的是协作者的资料，不是站长的。

**原因**：关于页资料按「最近更新优先」取一条。单作者的时候这没问题；**多作者之后，「最近更新的人」和「站长」就不再是同一个人了**——协作者一改资料，站长就被顶下去了。

**修法**：给白名单表加 `role` 列（`owner` / `author`，`owner` 用部分唯一索引保证全站唯一），取资料时 `role = 'owner'` 优先，只有站长没有资料时才回退到最近更新的协作者。

**启示**：**「单用户假设」在加第二个用户的那一刻就会变成 bug。** 排序、取唯一、默认值，这些地方都要回头检查一遍。

### 坑 8：邮箱比对没处理空格和大小写

**现象**：测试时用一个首尾带空格、大小写混杂的邮箱值去比对，判定成「无权限」。

**原因**：直接用 `=` 比对，`" WD43@FoxMail.COM "` 和数据库里的 `wd43@foxmail.com` 当然不相等。

**修法**：所有邮箱比对统一加一层归一化。

```sql
lower(btrim(email))
```

**启示**：**任何来自外部输入（请求声明、表单、导入数据）的标识符，比对前先归一化。** 这一类问题的特点是平时不出错，只在特定输入下出错，特别难复现。

## 六、白名单权限模型到底长什么样

把上面的坑修完之后，权限模型是这样的：

- **名单表对客户端完全不可读。** 开启 RLS 但**不建任何策略**，再 `REVOKE` 掉权限——连我自己写的测试脚本用登录态去 `SELECT` 都会被拒（`42501 permission denied`），前端只能通过一个函数拿到一个布尔值。
- **前端只负责提示，数据库才是裁判。** 后台会对无权限用户显示只读横幅并禁用「新建文章」，但这只是体验层；真正的拦截在数据库策略里，前端改一行 JS 绕不过去。
- **公开可见范围 = 白名单作者的已发布文章。** 陌生人的内容即使写进了表，也不会出现在首页、标签页和相关阅读里。

**越权实测**是最有说服力的一步：伪造一个「已登录」的身份声明直接打数据库，验证四件事——

| 攻击动作      | 结果     |
| --------- | ------ |
| 陌生人发文     | 被拒     |
| 陌生人读他人草稿  | 返回 0 行 |
| 陌生人修改站长文章 | 影响 0 行 |
| 陌生人读白名单   | 权限拒绝   |

这四条都过了，才算真的「安全」，而不是「看起来安全」。

## 七、几个查起来很费时间的小问题

- **本地端到端验证不用下载 Chromium。** 用 `playwright-core` 并显式指定本机已安装的 Chrome 路径即可。省掉 500MB 的下载，也避免版本错配。
- **断言计数是 0 的时候，先核对选择器。** 我曾经把正文容器写成 `.post-body`，而实际类名是 `.article`，结果误报「正文没渲染」，白查半天。**断言失败先怀疑断言本身。**
- **访问令牌里其实没有 email。** 解码后顶层只有 `azp / iss / sub / aud / exp / iat / jti`，会话对象里的用户也只有 `id`。服务端侧确实能拿到邮箱，但那是**网关转发时注入的声明**——依赖它就是一种隐式依赖。所以最终把权限函数改成「优先用 `auth.uid()` 反查邮箱，`auth.email()` 降级为兜底」，把隐式依赖变成显式查询。
- **数据库脚本工具一次只执行一条语句。** 批量改策略要用匿名块包起来：`DO $$ ... $$`。
- **云端存储的对象默认需要登录才能取。** 所以匿名访客看不到真实封面图，前端回退到渐变占位封面。这是**有意的设计取舍，不是 bug**——不登录就看得见图，意味着存储要对外开放，那才是更大的问题。

## 八、复盘：这些坑其实是三类

一条条列出来之后，会发现它们并不零散，大致可以归成三类：

1. **样式优先级类**（坑 2、3）。CSS 的层叠规则不直观，只能靠「基础规则在前、断点在后」和「兜底规则显式写」来约束。
2. **约定被打破类**（坑 1、4、5）。共用字段常量、手写导出清单、组件返回值——这些都是**靠约定在承重**，一旦漏掉一处，就静默失败，不报错、不崩溃，只是功能悄悄没了。
3. **验证盲区类**（坑 5、6、8，以及选择器误报）。这一类最值得警惕：前面两类的坑都是「本该报错却没报错」，而坑 5 更过分——**它是通过了测试的。**

所以最后的结论，其实只有两句话：

> 页面看起来正常，不代表权限是对的。
>
> 测试通过了，不代表路径是全覆盖的。

再补一句更落地的：**受保护的功能，一定把「进得去」和「进不去」两条路径都测一遍；涉及权限的判断，一定把「有权限的人」和「没权限的人」都试一遍。**

八个坑里，真正危险的从来不是那些报错的——报错会逼你去修。危险的是那些**安静地做错了事**的。
